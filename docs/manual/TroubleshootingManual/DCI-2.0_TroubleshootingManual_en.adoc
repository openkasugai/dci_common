== Introduction

This document describes troubleshooting for the DCI-2.0 System,
targeting tasks performed by DCI Operators and Tenant Operators.

=== Notes on Environment and Version Differences

The screen captures, command examples, execution results, and verification results described in this document are examples for explanatory purposes.
Depending on the environment in use, software version, and configuration status, display content and wording may differ partially; however, as long as they do not significantly deviate from the described content, this does not affect whether procedures can be executed or whether results are correct.

=== Notes on Chapter Classification

Some issues occur in both the DCI Management Cluster and the DCI Tenant Logical Infrastructure.
If you cannot find the relevant issue in one chapter, also check the other chapter.

=== Actions When Pod Repeatedly Enters CrashLoopBackOff

This section describes how to handle the case where the xxx-node-feature-discovery-worker-yyy Pod repeatedly enters CrashLoopBackOff. This issue may occur when adding Nodes.

The following describes an example where node-feature-discovery-worker Pods of gpu-operator and network-operator repeatedly enter CrashLoopBackOff.

. Check the Daemonset name.
+
[source, console]
----
$ kubectl get daemonsets.apps -n gpu-operator 
$ kubectl get daemonsets.apps -n nvidia-network-operator
----

. Restart the Pod.
+
[source, console]
----
$ kubectl rollout restart ds -n gpu-operator gpu-operator-node-feature-discovery-worker
$ kubectl rollout restart ds -n nvidia-network-operator network-operator-node-feature-discovery-worker
----

. Check the Pod status.
+
[source, console]
----
$ kubectl get pod -n gpu-operator 
$ kubectl get pod -n nvidia-network-operator 
----

==== For k8s-dra-driver-gpu kubelet plugin Pod
This section describes how to handle the case where the k8s-dra-driver-gpu kubelet plugin Pod repeatedly enters CrashLoopBackOff.

* Issue
+
--
The k8s-dra-driver-gpu kubelet plugin Pod repeatedly enters CrashLoopBackOff.

[source, console]
----
$ kubectl get pod -n dra-driver-nvidia-gpu -o wide 
NAME                                               READY   STATUS             RESTARTS        AGE     IP                NODE                         NOMINATED NODE   READINESS GATES
dra-driver-nvidia-gpu-controller-b94fd47b6-5kzzw   1/1     Running            0               2d12h   192.168.117.59    d1-f01-cots-control01.maas   <none>           <none>
dra-driver-nvidia-gpu-kubelet-plugin-w2h2p         0/2     CrashLoopBackOff   34 (100s ago)   46m     192.168.117.215   d1-f01-pgcdi-compute02.maas        <none>           <none>
----

Check the Pod causing CrashLoopBackOff with describe.
[source, console]
----
Events:
  Type     Reason          Age                  From               Message
  ----     ------          ----                 ----               -------
  ...
  Warning  Unhealthy       5s (x7 over 2m25s)   kubelet            Liveness probe failed: timeout: failed to connect service "10.245.117.215:51516" within 10s: context deadline exceeded <1>
----
<1> This applies when a LivenessProbe timeout has occurred.
--

* Cause
+
--
The above issue occurs when LISTEN on both ports 51515 and 51516 has not completed.
In the following example, only 51515 is in LISTEN state, and 51516 is not in LISTEN state.
[source, console]
----
$ kubectl exec -it -n dra-driver-nvidia-gpu dra-driver-nvidia-gpu-kubelet-plugin-w2h2p -- bash
Defaulted container "compute-domains" out of: compute-domains, gpus, init-container (init)
bash-5.2# netstat -tuln
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State       
tcp        0      0 :::51515                :::*                    LISTEN 
----
--

* Action
+
--
Because LISTEN on the port takes time, extend the LivenessProbe wait time (timeoutSeconds).
By default, it is set to 10 seconds, and you can extend it by increasing this value as needed.

[source, console]
----
$ kubectl -n dra-driver-nvidia-gpu edit daemonsets.apps dra-driver-nvidia-gpu-kubelet-plugin
  ...
        livenessProbe:
          failureThreshold: 3
          grpc:
            port: 51516 <1>
            service: liveness
          periodSeconds: 30
          successThreshold: 1
          timeoutSeconds: 10　　<2> 
----
<1> For all livenessProbes where `grpc.port` corresponds to the port that was not in LISTEN above,
<2> increase the value of `timeoutSeconds`.
--

=== When Errors Occur During PG-CDI Logical Server Operations

After power restoration or when specific units restart during operations, errors may occur in logical server operations because the PG-CDI startup order is not preserved. +
Specifically, issues may occur such as SSD resources built into the logical server entering failure status and commissioning by MAAS failing. +
In this case, execute the "Power Cycle Procedure" chapter in the PG-CDI "System Construction Procedure Manual" and restart the PG-CDI system.

==== Countermeasures for Component Deployment Failures
This section describes the rollback procedure when component deployment fails during component deployment.

The basic rollback flow is to uninstall the component that failed deployment from the DCI Manager,
and then perform reinstallation.

NOTE: Components can also be uninstalled by deleting the labels added during component deployment.

=== Actions When the GPU MIG Partition Policy Can No Longer Be Changed

This section describes how to recover when subsequent MIG partition policy changes can no longer be performed after executing a policy change operation on a GPU currently in use.

The MIG partition policy can be changed for the GPU on each node. However, if a policy change is executed on a GPU currently in use (for example, assigned to a DCI Application), the change process may fail, and subsequent policy changes may no longer be possible.

* Prerequisite
+
--
Available MIG partition policies can be checked with the following command.

[source, console]
----
$ kubectl --kubeconfig=/home/cloud-user/tenant-for-{tenant namespace}.kubeconfig describe cm -n gpu-operator custom-mig-parted-configs
----
Select a policy from the `mig-configs[]` list in `config.yaml:` included in the command output.

The MIG partition policy of the GPU on the target node can be changed with the following command.

[source, console]
----
$ kubectl --kubeconfig=/home/cloud-user/tenant-for-{tenant namespace}.kubeconfig label nodes <node name for MIG partitioning> nvidia.com/mig.config=<MIG partitioning policy> --overwrite	
----
--

* Symptom
+
--
If the MIG partition policy is changed for a GPU in use, the change process fails, and afterward changing to other policies becomes impossible.
When this issue occurs, the following logs are output.

.mig-manager log	
[source, console]
----
level=error msg="\nThe following GPUs could not be reset:\n  GPU 00000000:D5:00.0: In use by another client\n\n1 device is currently being used by one or more other processes (e.g., Fabric Manager, CUDA application, graphics application such as an X server, or a monitoring application such as another instance of nvidia-smi). Please first kill all processes using this device and all compute applications running in the system.\n"

level=debug msg="Running apply-exit hook"

level=fatal msg="Error applying MIG configuration with hooks: error resetting all GPUs: exit status 255"
----

.dmesg on the target node
[source, console]
----
[975580.582841] NVRM: nvCheckOkFailedNoLog: Check failed: Requested object not found [NV_ERR_OBJECT_NOT_FOUND] (0x00000057) returned from gisubscriptionGetGPUInstanceSubscription(pRsClient, RES_GET_HANDLE(pSubdevice), &pGPUInstanceSubscription) @ kernel_mig_manager.c:3091
----
--

* Corrective Action
+
--
If this issue occurs, recovery is possible by rebooting the affected node. However, because the Tenant Operator cannot directly access the node, request handling from the DCI Operator.

When rebooting, perform scheduling control to evacuate workloads.

. Exclude the target node from scheduling
+
[source, console]
----
$ kubectl cordon <target node name>
----
+
Wait until DCI Applications on the target node are evacuated to other nodes.

. Contact the DCI Operator and reboot the target node
+
The Tenant Operator cannot access the node via SSH or perform operations on the node. +
Therefore, node reboot must be performed by the DCI Operator.
+
After reboot, wait until the target node becomes `Ready`.

. Return the target node to scheduling	
+
[source, console]
----
$ kubectl uncordon <target node name>	
----
--





=== Actions When Node Manual Addition by NodeScalingRequest Fails
This section describes actions to take when node manual addition by NodeScalingRequest fails.
Execute the following corrective action according to the occurred symptom.

==== If Node Scale-Up Fails (Failure While Increasing Replicas of an Existing MachineDeployment)
This section describes corrective actions when adding a server of an existing configuration that has already existed in the tenant fails. In this case, increasing the replica count of an existing MachineDeployment has been performed to add the server of the existing configuration to the tenant.

When recovering from a failure state, check the failure status (progress phase/cause) and execute the necessary steps. For example, if failure occurred before creating/changing a certain resource, skip the deletion/modification step for that resource.

. Check the NodeScalingRequest name, and delete the NodeScalingRequest.
+
.Command Example
[source, console]
----
$ kubectl --kubeconfig=/home/cloud-user/tenant-1-sa.kubeconfig get nodescalingrequest -n tenant-1
$ kubectl --kubeconfig=/home/cloud-user/tenant-1-sa.kubeconfig delete nodescalingrequest <NodeScalingRequest name> -n tenant-1
----
. Get the MachineSet related to the MachineDeployment, and set `true` for `PausedAnnotation ("cluster.x-k8s.io/paused")`.
. If label `"scaling.my.domain/in-progress-uid"` is assigned to the MachineDeployment, delete it.
. Decrease the replica count of the MachineDeployment by 1.
. Delete the target Machine.
. Delete `PausedAnnotation ("cluster.x-k8s.io/paused")` of the MachineSet set in Step 2.

Normally, when Step 1 is executed, the NSR controller automatically executes Steps 3 and 6 as well.
However, if processing has stopped midway due to communication failure with the Management Cluster, etc.,
manual action is required.
On the other hand, Steps 2, 4, and 5 are not executed by the NSR controller,
so if failure occurs after processing has progressed to these phases,
always execute them manually.

As additional information, even if a LogicalServer exists before provisioning is complete,
if the API Server and DB are operating normally,
no action is required because deleting the Machine in Step 5 also deletes the LogicalServer in linkage.

==== If Adding a Server of a New Configuration Fails (Failure While Creating a New MachineDeployment)
This section describes corrective actions when adding a server of a new configuration that has not existed in the tenant fails. In this case, creation of a new MachineDeployment (and DCIMachineTemplate) has been performed to add a server of the new configuration to the tenant.

When recovering from a failure state, check the failure status (progress phase/cause) and execute the necessary steps. For example, if failure occurred before creating/changing a certain resource, skip the deletion/modification step for that resource.

. Delete the NodeScalingRequest.
. Check the DCIMachineTemplate referenced by the MachineDeployment.
+
.Execution Steps
[source, console]
----
$ kubectl get machinedeployment \
  -n tenant-1 <machinedeployment-name> \
  -o jsonpath='namespace={.metadata.namespace}{" name="}{.spec.template.spec.infrastructureRef.name}{"\n"}'
  
namespace=tenant-1 name=worker-1  # Outputs the referenced DCIMachineTemplate name and Namespace
$ kubectl get dcimachinetemplates.infrastructure.cluster.x-k8s.io -n tenant-1 worker-1
NAME       AGE
worker-1   10h
$
----
. Check the MachineDeployment name, and delete the MachineDeployment.
+
.Execution Steps
[source, console]
----
$ kubectl get machinedeployment -n tenant-1
$ kubectl delete machinedeployment <MachineDeployment name> -n tenant-1
----
. Delete the DCIMachineTemplate checked in Step 2.

By deleting the MachineDeployment, Machine, DCIMachine, and LogicalServer are also deleted due to OwnerReference and related mechanisms. After deleting the MachineDeployment above, wait until each resource disappears, and after confirming all resources are deleted, retry node addition again.

If a pre-prepared DCIMachineTemplate is to be used when retrying node manual addition after recovery, skip 2 and 4.

=== Actions When Applying Resource Claim Template Fails
When applying a Resource Claim Template, if the API version supported by the cluster does not match the `apiVersion` described in the manifest, application fails.
In that case, fix the `apiVersion` of the Resource Claim Template.

* Symptom
+
--
When applying the Resource Claim Template, an error indicating API version mismatch occurs as follows.

.Log Output Example
[source,console]
----
$ kubectl apply -f resourceClaimTemplates-gpu.yaml
resource mapping not found for name: "single-gpu" namespace: "dci" from "resourceClaimTemplates-gpu.yaml": no matches for kin
d "ResourceClaimTemplate" in version "resource.k8s.io/v1beta1"
ensure CRDs are installed first
...
----
--
+
* Cause
+
--
The API version of the Resource Claim Template supported by the cluster and
the `apiVersion` described in the manifest do not match.

.API version supported in the K8s Cluster
[source,console]
----
$ kubectl api-versions | grep resource.k8s.io
resource.k8s.io/v1
----
From the result above, it is clear that `resource.k8s.io/v1` is supported by the cluster.

.apiVersion of the Resource Claim Template
[source,yaml]
----
apiVersion: resource.k8s.io/v1beta1
kind: ResourceClaimTemplate
metadata:
  name: single-gpu
  namespace: dci
spec:
  spec:
    devices:
      requests:
      - name: t4
        deviceClassName: gpu.nvidia.com
        selectors:
        - cel:
            expression: "device.attributes['gpu.nvidia.com'].productName=='Tesla T4'"
----
In the manifest, `resource.k8s.io/v1beta1` is specified,
and it does not match the API version supported by the cluster.

--
+
* Corrective Action
+
--
Change the `apiVersion` of the Resource Claim Template
to the API version supported by the cluster.

In addition, because the definition format of Resource Claim Template has changed with the API version change,
fix the manifest as follows in addition to fixing `apiVersion`.

.Modification Example 
[source,yaml]
----
apiVersion: resource.k8s.io/v1              <1>
kind: ResourceClaimTemplate
metadata:
  name: single-gpu
  namespace: dci
spec:
  spec:
    devices:
      requests:
      - name: t4
        exactly:                            <2>
          deviceClassName: gpu.nvidia.com   <3>
          selectors:
          - cel:
              expression: "device.attributes['gpu.nvidia.com'].productName=='Tesla T4'"
----
<1> Change the API version to "v1"
<2> Add "exactly" immediately after name
<3> Shift the subsequent indentation

=== Actions When the SR-IOV Device Plugin Pod Is Not Deployed and VF Is Not Created
This section describes actions to take when VF is not created even though NVIDIA Network Operator has been deployed and the SriovNetworkNodePolicy resource has been created.
This action assumes a situation where the SR-IOV Device Plugin pod (sriov-device-plugin-xxxx) is not created, and attempts deployment of the SR-IOV Device Plugin.

* Check the cause of SR-IOV Device Plugin not being deployed

. Check node labels (@DCI Tenant Logical Infrastructure Control Plane)
+
Use the following command to check labels of the node where VF has not been created. Verify that SR-IOV Device Plugin is disabled.
+
.Execution Steps
[source, console]
----
$ kubectl describe node <node name> | grep sriovnetwork.openshift.io/device-plugin
----
+
.Command Example / Execution Result
[source, console]
----
$ kubectl describe node xxxx.maas | grep sriovnetwork.openshift.io/device-plugin
                    sriovnetwork.openshift.io/device-plugin=Disabled
----

* Recovery of SR-IOV Device Plugin

. Try reapplying labels (@DCI Tenant Logical Infrastructure Control Plane)
+
Use the following command to restart Node Feature Discovery, re-detect node hardware information, and register that information in Kubernetes as node labels.
+
.Execution Steps
[source, console]
----
$ kubectl rollout restart daemonset -n nvidia-network-operator network-operator-node-feature-discovery-worker
----
+
.Command Example / Execution Result
[source, console]
----
$ kubectl rollout restart daemonset -n nvidia-network-operator network-operator-node-feature-discovery-worker
daemonset.apps/network-operator-node-feature-discovery-worker restarted
----

. Check that SR-IOV Device Plugin is enabled (@DCI Tenant Logical Infrastructure Control Plane)
+
Use the following command to check labels of the node where VF has not been created. Verify that SR-IOV Device Plugin is enabled.
+
.Execution Steps
[source, console]
----
$ kubectl describe node <node name> | grep sriovnetwork.openshift.io/device-plugin
